根据你的应用场景（个人电脑、代码可见、频繁修改、侧重防文件误删或越界访问，且不惧死循环），最核心的诉求其实是文件系统的细粒度访问控制。
在不希望使用 Docker 这类重型沙箱带来性能损失的前提下，针对你的需求，以下是最佳的两种落地架构方案：
------------------------------
## 方案一：使用系统级“极轻量”微型沙箱（推荐，对性能零影响）
既然在个人电脑上运行，可以利用操作系统自带的低开销安全隔离功能。这类方案既有原生的性能，又能完美限制文件读写。
## 1. Windows 环境：利用 icacls 派生低权限进程（最简单）
如果你的电脑是 Windows，可以通过 subprocess 启动一个低权限（Low Integrity Level）的子进程来执行 LLM 代码。

* 原理：Windows 的低权限进程默认无法写入你个人用户的大部分文件夹（如文档、C盘等），只能读写特定的临时目录。
* 实现：创建一个只读的专属工作区文件夹，通过 Python 为子进程剥夺系统管理员和普通用户权限。

## 2. Linux 环境：使用 Bubblewrap（高性能沙箱外壳）
如果你在 Linux（或 WSL）下开发，Bubblewrap（很多 Linux 桌面应用如 Flatpak 底层都在用）是完美的解决方案。

* 为什么快：它利用 Linux 的命名空间（Namespaces）进行隔离，没有虚拟化开销，性能损失为 0%。
* 配置方式：

# 仅允许读取 python 环境和指定的 input_dir，且输出只能写到 output_dir
bwrap --ro-bind /usr /usr \
      --ro-bind /lib64 /lib64 \
      --ro-bind /home/user/project/input_dir /workspace/input \
      --bind /home/user/project/output_dir /workspace/output \
      --unshare-all \
      python /workspace/input/llm_code.py

通过这种方式，LLM 代码哪怕写了 os.system("rm -rf /")，它在沙箱里看到的 / 也是空的，根本碰不到你真实电脑的其他文件。

## 方案二：代码级防误触拦截器（如果你绝对不想引入外部工具）
如果你希望纯 Python 解决，且“防君子不防小人”（因为人类可见源码，主要怕 LLM 写错代码导致误删），可以通过 动态猴子补丁（Monkey Patching） 在代码执行前，把所有文件操作的内置函数替换掉。
下面为你写一个现成的拦截器：

import osimport builtinsfrom pathlib import Path
class FileSandboxError(PermissionError):
    pass
def setup_file_interceptor(allowed_input_dir: str, allowed_output_dir: str):
    """
    轻量级文件拦截器
    允许读取 allowed_input_dir
    允许在 allowed_output_dir 创建新文件，但禁止修改/删除已有文件
    """
    INPUT_PATH = Path(allowed_input_dir).resolve()
    OUTPUT_PATH = Path(allowed_output_dir).resolve()

    # 记录初始化时，输出文件夹里已经存在的文件（禁止修改它们）
    existing_output_files = {p.resolve() for p in OUTPUT_PATH.glob('**/*') if p.is_file()}

    # 备份原生的 open 函数
    original_open = builtins.open

    def patched_open(file, mode='r', *args, **kwargs):
        file_path = Path(file).resolve()

        # 检查是否属于允许的目录
        is_in_input = file_path.is_relative_to(INPUT_PATH)
        is_in_output = file_path.is_relative_to(OUTPUT_PATH)

        if not (is_in_input or is_in_output):
            raise FileSandboxError(f"❌ 越界访问：禁止读写指定工作区以外的路径: {file_path}")

        # 检查写操作权限
        if any(m in mode for m in ['w', 'a', 'x', '+']):
            # 如果试图写输入文件夹，拒绝
            if is_in_input:
                raise FileSandboxError(f"❌ 权限拒绝：输入文件夹为只读: {file_path}")
            
            # 如果试图修改输出文件夹中【原本就存在】的文件，拒绝
            if file_path in existing_output_files:
                raise FileSandboxError(f"❌ 权限拒绝：禁止修改输出文件夹内已有的历史文件: {file_path}")

        return original_open(file, mode, *args, **kwargs)

    # 1. 替换全局 open
    builtins.open = patched_open
    
    # 2. 禁用高危的删除和重命名函数
    def banned_action(*args, **kwargs):
        raise FileSandboxError("❌ 权限拒绝：LLM 代码禁止调用删除、重命名或系统指令。")

    os.remove = banned_action
    os.unlink = banned_action
    os.rmdir = banned_action
    os.rename = banned_action
    os.system = banned_action
    
    # 如果引入了 shutil，也一同禁用
    try:
        import shutil
        shutil.rmtree = banned_action
        shutil.move = banned_action
    except ImportError:
        pass
# ================= 实际调用示例 =================if __name__ == "__main__":
    # 配置你的工作区
    setup_file_interceptor(
        allowed_input_dir="./data/inputs",
        allowed_output_dir="./data/outputs"
    )

    # LLM 生成的代码
    llm_code = """
# 正常的计算与保存
with open("./data/outputs/result.txt", "w") as f:
    f.write("计算结果")

# 试图越界读取系统文件（会报错）
with open("C:/Windows/win.ini", "r") as f:
    print(f.read())"""
    
    try:
        # 使用 exec 执行（由于代码可见，且死循环可以人工杀，exec 性能最好）
        exec(llm_code, {"__builtins__": builtins})
    except Exception as e:
        print(f"运行拦截成功: {e}")

## 💡 针对你场景的总结建议

   1. 如果你用的是 Windows：建议直接用上面的 方案二（Monkey Patching 拦截器）。它在纯 Python 下运行，完全零侵入、零性能损失。因为你有人类介入审计代码，这个拦截器足够防止 LLM 抽风写出 open('已有文件', 'w') 覆盖掉你原本的珍贵数据。
   2. 如果你用的是 Linux/WSL：强烈建议花 5 分钟了解一下 Bubblewrap。它通过一条命令启动，在操作系统内核层面帮你把文件夹“焊死”，代码哪怕想绕过 Python 的 open 去用 C 扩展读写文件也会被内核直接拦截，且运行速度和原生完全一样。

是的，方案一（系统级微型沙箱）完全是语言无关（Language-Agnostic）的。 [1, 2] 
因为它的隔离逻辑是在操作系统内核/系统层实现的，而不是在 Python 解释器内部。无论你让 LLM 生成的是 Python、C++、Go 还是 Rust 代码，只要它们最终被编译或执行为一个独立的操作系统进程，方案一的沙箱外壳就能100%生效。 [1, 3, 4] 
针对你“生成 C++ 代码、追求高性能、限定读写某个文件夹”的需求，以下是方案一在 C++ 场景下的工作原理、性能损耗分析以及具体实现。
------------------------------
## 一、 为什么方案一对 C++ 依然完美适用？
在 C++ 场景中，你的自动化流程通常是：
LLM 生成 C++ 源码 $\rightarrow$ 调用编译器（如 g++ / cl.exe）编译出可执行文件 $\rightarrow$ 运行该二进制文件。
当你运行编译出的 C++ 程序时：

   1. Linux 的 Bubblewrap：它利用的是 Linux 内核的命名空间（Namespaces）。它会为 C++ 进程捏造一个“虚拟的文件系统根目录”。在这个虚拟世界里，除了你分配给它的 input 和 output 文件夹，其他地方都是空的，C++ 代码里的 std::ofstream 就算写爆了也碰不到你电脑上的其他目录。 [2, 4, 5, 6, 7] 
   2. Windows 的低完整性级别（Low Integrity Level）：它利用的是 Windows 的强制性完整性控制（MIC）。当 C++ 进程被标记为 Low IL 时，Windows 操作系统内核会在句柄层拦截它。它只要尝试修改任何非 Low IL 的文件（即你电脑上大部分的普通文件），系统直接返回 Access Denied（拒绝访问），根本不需要 Python 参与。 [8, 9, 10, 11] 

## 二、 性能损耗有多少？
由于 C++ 是为了高性能，你一定很关心损耗。结论是：几乎为 0。

* Bubblewrap (Linux)：损耗为 0%。它不是虚拟机（如 VirtualBox），也不是传统容器（如 Docker 的分层镜像存储），它不经过任何虚拟化层。C++ 进程是直接由你本机的 CPU 执行的，内存读写、CPU 计算全部都是原生速度。 [2, 6] 
* Low Integrity (Windows)：损耗为 0%。Windows 在打开文件时本来就要检查 ACL 权限，Low IL 只是在原有的权限检查里多比对了一个安全标签，完全不会影响 C++ 的运行和计算速度。 [9, 10, 11]

## 三、 C++ 场景下的轻量沙箱落地代码## 1. Linux 环境（使用 Bubblewrap 运行 C++）
你只需要用 Python 的 subprocess 去调用 bwrap 启动编译好的 C++ 二进制文件即可。 [4] 

import subprocess
def run_cpp_in_linux_sandbox(binary_path: str, input_dir: str, output_dir: str):
    # 组装 Bubblewrap 命令
    # --ro-bind-try 目的是绑定 C++ 运行所需的系统动态链接库（ld, libc等）
    cmd = [
        "bwrap",
        "--ro-bind", "/usr", "/usr",
        "--ro-bind", "/lib", "/lib",
        "--ro-bind", "/lib64", "/lib64",
        # 将宿主机的输入文件夹，挂载为沙箱内的 /workspace/input（只读）
        "--ro-bind", input_dir, "/workspace/input",
        # 将宿主机的输出文件夹，挂载为沙箱内的 /workspace/output（可读写）
        "--bind", output_dir, "/workspace/output",
        # 将编译好的 C++ 程序挂载进去
        "--ro-bind", binary_path, "/workspace/app",
        # 彻底隔离网络、IPC、其他进程等
        "--unshare-all",
        # 切换到工作目录并执行
        "--chdir", "/workspace",
        "/workspace/app"
    ]
    
    # 零性能损耗运行
    result = subprocess.run(cmd, capture_output=True, text=True)
    return result.stdout

## 2. Windows 环境（使用低权限令牌运行 C++）
在 Windows 上，我们可以利用 Python 的 icacls 命令，动态地把 LLM 编译出来的 C++ 程序的安全标签降为 Low，然后再启动它。一旦降级，它将无法触碰你普通权限下的其他任何文件。 [8, 10, 11] 

import subprocessimport os
def run_cpp_in_windows_sandbox(exe_path: str, output_dir: str):
    """
    通过 Windows Mandatory Integrity Control (MIC) 降权运行 C++ 程序
    """
    # 1. 首先，为了让低权限的 C++ 能把结果写进输出目录，
    #    我们必须显式允许该输出目录接受 Low Integrity 的写入。
    subprocess.run(
        f'icacls "{output_dir}" /setintegritylevel (OI)(CI)L', 
        shell=True, stdout=subprocess.DEVNULL
    )
    
    # 2. 将编译出来的 C++ 文件的自身级别也设为 Low
    #    Windows 规定：Low 级别的程序文件，启动后自动变为 Low 级别进程
    subprocess.run(
        f'icacls "{exe_path}" /setintegritylevel L', 
        shell=True, stdout=subprocess.DEVNULL
    )
    
    # 3. 直接启动。此时这个 C++ 进程已经是“寸步难行”的低权限状态
    #    它只能读写刚才被我们标记为 L 的 output_dir 以及系统的 Temp 目录，
    #    如果它想修改你桌面上的文件或 C 盘的其他历史文件，Windows 内核会直接拦截。
    result = subprocess.run([exe_path], capture_output=True, text=True)
    return result.stdout

## 💡 为什么在这里不推荐方案二（代码级拦截）？
因为方案二（Monkey Patching）是通过修改 Python 的 builtins.open 来实现的。一旦 LLM 生成的是 C++ 代码，编译后的二进制文件直接跟操作系统内核打交道（调用 C 运行库的 fopen 或 Windows API），Python 的拦截器对它完全无效。
所以，面对 C++ 或多语言混杂的场景，方案一（系统级微型沙箱）是唯一且最完美的解法，既做到了多语言通用，又保住了 C++ 原生的极致性能。 [2, 6]
