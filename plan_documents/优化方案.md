1. 注意需要考虑将来伪泛型的架构，经过分析：
   - Cython 的 fused 并不支持加入到 vector
   - Cython 的 IF 已经被认为准备弃用
   - 函数指针方案会增加运行开销，只用在必要之处
2. 为了测试方便编程，保持基类对链表的兼容性的同时，修改二叉树。
3. 将原 safe_iter_kit.pyx 拆分为如下部分：
   - safe_iter_base.c （用宏编程当链表时去掉大整数的内存占用，需要包含所有涉及 RevisitEntry 定义的方法）
   - container.h （我已经实现在 tools\container.c，调用库的确保正确）
   - safe_iter.pyx （Cython代码）
4. prepare_next 架构：
   - 方案一： 定义一个兼容 C 的全局/静态函数作为桥梁，用到 Context 架构
   - 方案二： 直接定义链表和树的 C 版 _prepare（需要解决在 C 内获取 attribution），再由各自 Cython 代码初始化（不能将节点改为纯C，因为用户端必须是纯Python）
5. 多态新架构：
   - 共同点分析：
     - 因为 utarray_push_back 是根据注册时元素的大小来 push 的，但是这种方案编译器不保护，容易出错
     - 若是将 safe_iter_check_safe 进行宏模板，又会使得代码量剧增
     - 发现无论 safe_iter_check_safe 是否成功，被检查的 entry 都会 PUSH 到 revisit
     - 原 revisit 包含了所有 iter 输出的节点，可以还原 iter 输出
     - 原 revisit 的名字容易误导，不如改为 check_seq，uf_index 改为 c_index，RevisitEntry 改为 CheckEntry
   - 链表所需分析：
     - 当链表无环时，check_seq 按序遍历即为 iter 遍历
     - 当链表有环（出现环）时，仅 check_record[-1] 为重复节点，其余都是合法按需输出的节点
   - 树所需分析：
     - check_record 顺序不代表遍历顺序，因为检查不一定是输出，有可能只是用于入栈、队列
     - 因此需要维护一个 iter_out_uf_idx （原） （名字不太好，可能要换），才能还原迭代结果
     - 堆索引用的 vid 的名字与 check_record 容易混淆，换为 heap_index （局部变量用 hp_i） 可能更精准
     - 为了方便从容器直接PUSH到 check_seq，将原 IterNode 改为与 check_record 相同的结构，取消 IterNode。
  - 最佳方案——队尾原地修改：
    - safe_iter_check_safe 无需传入 entry，而是将 check_record[-1] 作为被检查对象，若重复原地修改 check_record[-1].c_index 指向重复索引
    - 取消 cur，因为 cur 可以从 check_record 的队尾附近提取，cache 命中率有保障：
      - 对于链表可以用 check_record[-1] 替代
      - 对于树的遍历同样可以用 check_record[iter_out_uf_idx[-1]]（如），还可以保持读取完整地信息（包括树的 vid），而不需要对 safe_iter 进行宏泛型。
      - 树的栈、队元素中的 checked 字段直接替换为 c_index 为 -1 表示没有检查过，其他值则代表在 check_record 注册的下标。如此 iter_out_uf_idx 的赋值则可以通过 pop 出容器的 c_index 获得。
    - safe_iter_check_safe 返回 BOOL 类型，因为无论链表还是树，都需要修改为布尔，而返回 -1 为安全和 其他为重复节点，都需要额外增加一次比较操作。
    - 对于树，从栈、队列中直接 pop 元素 PUSH 到 check_record 是更佳。
6. 因此最终方案：：
   - 将  stack（queue）统一为容器结构体，通过函数指针实现  stack（queue）的泛型，加入到 SafeIterBase（已用 container 初步实现）
   - SafeIterBase 尽量做到链表和树共用一套编译后的代码，通过 utarray.h 的泛型实现
   - TreeIterBase 版的 CheckEntry 中的 hp_i 和 early_stop 仅树需要用，而链表是不需要的，因此只需要在 TreeIterBase 中定义即可
   - cheak_safe 的引用计数管理（仅当新增 _seen 节点 +1，因为最终释放时是以 _seen 为准），而外部如链表和树的栈队等各自分别管理。   
   - C语言写的迭代类，为了方便定义节点在 check_record 中的下标，改为以 CheckEntry 为单位返回，如此可方便需要返回节点本身和位置的 flatten 高效迭代。
   - 注意利用结构体成员顺序进行C多态，使得“继承类”的 check_record 等元素可以被基类识别其共同前缀成员。
   - 删除 safe_iter_flatten_entrys，因为可以直接从 check_record 中读取 可直接在 Cython 中实现对应逻辑
   - 请重点落实“队尾原地修改”方案，给出具体需要修改的代码！
7. 将来需要注意的：
   - TreeIterBase 大整数要求高性能，已部分 C 化（bigint_vid.h）
   - 智能缓存机制：通过 check_record 还原链表、树（需要配合下标序列）的迭代，而无需从头开始

## 🔮 下一步计划（更新版）
1. **SafeIterBase Cython 加速**  
   - 操作对象从原生节点改为 Cython 节点指针  
   - `_seen` 存储节点指针 → 首次出现索引  
   - `_revisit` 存储 `CheckEntry`（含节点指针、`c_index`、可选 `heap_index`）  

2. **容器层统一**  
   - `stack` / `queue` 使用 `UT_array` 存储 `IterNode`（与 `CheckEntry` 同构）  
   - 删除独立的 `vid_list`，所有索引信息存入 `_revisit`  

3. **队尾原地修改（已实现核心）**  
   - `safe_iter_push_raw` + `safe_iter_check_tail` 合并操作  
   - 取消 `cur` 字段，仅保留 `cur_index` 指向当前输出  

4. **树遍历器泛型化**  
   - 通过操作字符串（`"LR"`, `"RCL"` 等）统一前/中/后/层序  
   - 栈/队列元素直接 push 到 `check_record`，无需单独 `checked` 标志  

5. **多态复用**  
   - 链表和树共用同一套 `SafeIterBase` 编译代码  
   - 树特有字段（`heap_index`、`early_stop`）仅在 `TreeIterBase` 中定义  

6. **C 层 `prepare_next` 桥接**  
   - 保留 `ctx` + 函数指针，由 Cython 子类实现 `_prepare_next`  
   - 避免宏泛滥，保持可维护性  

7. **将来注意**  
   - `bigint_vid.h` 已 C 化，支持大整数堆索引  
   - 智能缓存：通过 `check_record` 还原迭代，无需重复遍历  

8. **核心节点 Cython 化 + 框架注入（删除 KitBase）**  
   - **节点定义**：  
     - `cdef class ListNode` / `TreeNode`  
     - `cdef public ListNode next`（C 指针，迭代零开销）  
     - `cdef public object val`（Python 对象，兼容任意类型）  
   - **方法内置**：  
     - `cpdef flatten(self)`、`__iter__` 等直接操作 C 字段  
     - 环检测与 `SafeIterBase` 集成，无需包装层  
   - **注入机制**：  
     - `SolutionRunner` 执行前注入 `globals()['ListNode'] = CythonListNode`  
     - 学生代码完全无感，`class Solution` 中直接使用  
   - **删除 KitBase**：不再需要代理类，节点本身即高性能 Cython 对象  
   - **性能收益**：链表遍历速度提升 3~5 倍，树遍历提升 2~4 倍
